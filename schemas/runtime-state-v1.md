# Runtime state schema v1

FR-003 introduces the first SQLite runtime schema. The executable migration is [001-runtime.sql](../packages/state/migrations/001-runtime.sql), bundled with the state adapter so it works from an unrelated working directory. There is no prior MZ runtime schema to convert.

| Table               | Contents                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `schema_migrations` | Contiguous version, migration name, SHA-256 of SQL, UTC application timestamp                             |
| `events`            | Append sequence, unique UUID, event enum, actor UUID, occurrence timestamp, optional run/inbox references |
| `inbox_items`       | UUID, private source UUID reference, receipt timestamp                                                    |
| `runs`              | UUID, worker UUID, start/finish timestamps, nullable terminal outcome enum                                |

SQL uses STRICT tables. Events reference run/inbox records through foreign keys. UPDATE and DELETE triggers protect events; a BEFORE INSERT trigger also rejects collisions from REPLACE, including on connections with recursive triggers disabled. An administrator with schema access can still remove triggers; workers receive no raw SQL interface.

No raw intake, description, token, payload, transcript, task priority, milestone, or editable work-status column exists. Run outcomes describe execution and do not compete with GitHub planning fields. Source UUIDs identify content managed outside this adapter; private intake retention and source storage belong to M-02.

## Migration contract

- Application identity is SQLite `application_id = 0x4d5a5354` (MZST).
- `user_version` equals the number of applied contiguous migrations.
- The ledger verifies versions, names, and checksums. SQLite schema objects must match the schema generated by those migrations, not just have the same names.
- Only a new empty database or a recognized consistent MZ database is accepted. Foreign databases and future/changed/inconsistent histories fail safely; no downgrade or automatic repair is attempted.
- Schema changes require a new numbered SQL migration. Never edit applied SQL. Migrations must not include transaction-control statements; the runner owns BEGIN IMMEDIATE, COMMIT, and ROLLBACK.
- The migration, ledger update, and version change share a transaction. Initial or incremental failure rolls back DDL and existing records remain intact. Existing schema integrity is checked before applying an upgrade.
- WAL, foreign keys, recursive triggers, FULL synchronization, and a 250 ms busy timeout are required by the adapter.

Migration tests use real synthetic SQLite databases, including a simulated second migration to prove upgrade and failure behavior. FR-005 subsequently adds [schema v2](runtime-state-v2.md) and backup/restore verification; migration 001 remains unchanged.
