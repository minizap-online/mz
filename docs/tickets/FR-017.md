# FR-017 — Prepare project checkouts with renewable repository delivery credentials

## Owner requirements

MZ prepares a folder and authenticated checkout so the owner can start Codex
there. The owner requests sufficient authority in that one GitHub repository to
implement and deliver applications: code, issues, milestones, workflows, repository
settings, deployment environments, Pages, secrets and variables. Existing project
workflows remain usable. Code/issues-only credentials are insufficient.

Repository credentials must be renewable without exposing the App signing key or
relying on global personal credentials. Access is scoped to a GitHub repository,
not a filesystem copy. Credential values must not enter checkout .env files,
Git, company context, logs or SQLite. Local activation may use nonsecret references.

This is manual owner-assisted preparation, not an M-06 scheduler. Cross-project
security/maintenance roles are a future need rather than initial scope.

## Proposed boundaries and dependencies

Build on FR-015 and complement [FR-016](FR-016.md). Define an explicit delivery
permission profile for repository Contents, Issues, Pull requests, Actions,
Workflows, Administration, Environments, Deployments, Pages, Secrets, Variables,
Checks and Commit statuses. Map exact API grants and endpoint support during
design. Organization policies and GitHub plan limitations still apply; this is
not a claim of universal GitHub administration. Destructive operations are not
implied by the owner's request to create delivery infrastructure.

Modern GitHub Projects have organization/user scope. Repository selection on a
token is not a per-board authorization mechanism. Proposed default: the steward
manages linked organization boards while project workers use repository-specific
credentials. Any restricted worker board interface needs its own explicit design.
Issues can represent features/tasks/bugs and milestones can group delivery goals.

GitHub access does not grant VPS SSH, DNS, hosting-account or registry access.
Deployment needs separately provisioned project credentials and target details.
Developer App credentials and workflow runtime credentials are distinct. Provision
secret values through protected native channels, not model conversation; GitHub
does not return stored Actions secret values through its read APIs.

The existing exact App grant allowlist and repository token subset omit delivery
permissions. Update MZ's profile compatibility and diagnostics before guiding the
owner through GitHub's required approval of additional grants. Preserve human
organization ownership and existing credentials; no broad personal-token fallback.

A helper must renew repository-only credentials. The current shared OS account
holding the App key is not an isolation boundary against untrusted code. Session
host topology remains to be established; a separate-host/untrusted-worker broker
requires explicit design. Checkout and activation interfaces also await design.

## Acceptance to refine in the design

- [ ] Agree delivery grants, App installation upgrade and session host boundaries.
- [x] Prepare a new checkout without global personal credential fallback or token
      values in URLs, argv, context, checkout environment files or logs.
- [x] Renew Git/gh credentials with exactly the selected repository and approved
      delivery permissions; keep organization administration out of worker tokens.
- [x] Preserve and reconcile existing/dirty/wrong-repository destinations.
- [x] Distinguish permission readiness, verified delivery and missing VPS/DNS/secret
      prerequisites. Do not claim deployment merely from a successful checkout.
- [x] Test scoping, renewal, safe failure, profile compatibility and preservation
      using synthetic fixtures. Actual App permission approval is an owner step.

## Session evidence

The owner explicitly requested implementation and prioritized getting both new
projects developing through tickets immediately. Execution uses the bounded
[delivery plan](../superpowers/plans/2026-10-30-project-delivery.md), with native
implementation and final independent review; broad FR-016 remains separate.

Initially registered before implementation. Source tracing confirmed `appPermissions`,
`checkPermissions` and `withRepositoryToken` use exact narrow grant sets. Official
GitHub documentation was consulted. At initial registration no App settings,
credentials, checkouts, remote issues or deployment resources had changed; the
initial documentation-only checks did not rerun runtime tests.

Implementation evidence: permission-profile tests first failed against legacy-only
validation, then passed with exact legacy/delivery profiles and per-operation
repository-only tokens. Checkout tests first failed against the missing command,
then passed with actual local Git metadata and a synthetic clone boundary. Native
helper tests reject cross-project requests before issuing credentials. Existing
destinations/instructions are preserved; explicit delivery mode fails before
creating a destination when grants are missing.

Independent review found one Important inherited-personal-authentication problem;
plain Git after activation reproduced it RED. Activation/config isolation and
local conflicting-auth refusal fixed it; both regressions pass. The minor gh-api
flag guidance was corrected. No deferred findings. Full check passes build, lint,
formatting and 489/489 tests; typecheck and diff checks pass.

Installed the implementation behind the existing development launcher. Real App
status succeeds. Two owner-selected private repositories were cloned and received
local ticket instructions/activation, foundation milestones, workflow labels and
initial FR-001 issues. No product code, dependency installation or deployment was
performed. The existing App installation lacks delivery grants; `mz github
permissions` reports them and the owner upgrade path. Real delivery readiness is
pending GitHub's owner approval, not proven by synthetic token tests. Basic
code/issue/PR access works with the current profile; the broader FR-016 steward
feature is not claimed implemented. No connection/SQLite schema was changed.

Live activated-session verification exposed an in-flight App registration update
and GitHub's canonical Variables key, actions_variables. A synthetic regression
reproduced validation failure RED; compatible allowlisted registration/install
validation and the canonical key fixed it. Known repository-only optional grants
(artifact metadata, merge queues, packages, hooks and repository Projects) can be
included in delivery tokens when actually granted; unknown or expanded
organization grants remain rejected. Diagnostics now distinguish missing
registration permissions from missing installation approval. This supersedes the
initial exact-two-profile assumption while preserving exact token-response checks.
The final full suite passes 490/490 tests with build/lint/format and typecheck.
Both actual activated project sessions successfully ran ordinary Git remote checks
and read their starting issues. No credentials were printed or persisted in the
checkouts. GitHub issue synchronization follows; private Project synchronization
remains separate because project worker tokens omit organization grants.
