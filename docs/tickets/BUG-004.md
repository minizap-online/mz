# BUG-004 — Accept repeated Git credential capability and challenge fields

## Reproduction and root cause

The owner completed browser App setup, but init failed at repository connection. Read-only live diagnostics confirmed the saved App/installation/owner verification, repository metadata access and narrowed token validation succeed. The actual Git HTTP credential request contains capability[] twice plus wwwauth[]. MZ rejects every duplicate field, so the helper quits before supplying its credential. The prior synthetic Git fill test omitted HTTP capability negotiation and did not reproduce this input class.

## Expected behavior

Accept Git's repeated advisory array fields capability[], wwwauth[] and state[] while continuing to reject duplicate routing/scalar fields such as host, protocol or path. The helper keeps its legacy username/password response and remains fail-closed on invalid scope/authentication. A repository-connection failure after App setup should explain saved App reuse rather than suggesting duplicate registration/import.

## Acceptance

- [ ] RED/GREEN actual Git credential flow with repeated capability/challenge fields; malformed duplicate identity fields still refuse with quit=true before provider use.
- [ ] App grant/owner checks, repository scope and secret-output boundaries remain intact.
- [ ] Repository failure guidance identifies saved App reuse and same-request retry.
- [ ] Full checks, review, CI and installed read-only live repository access verified. No new App registration, permission changes, company context creation or credential values in logs.

Observed RED: the real Git credential-fill regression with repeated capability/challenge fields failed with helper quit; GREEN after ignoring advisory/unrecognized attributes while validating identity fields. Duplicate protocol/host/path still return quit=true without supplying credentials. Repository failure guidance was reproduced RED/GREEN and now points to saved App reuse. Full check passed 478 tests plus build/lint/format and typecheck. A read-only live Git ls-remote probe using the corrected helper and the existing owner-approved App succeeded; no refs, token or key values displayed. Independent review and delivery follow.

Independent scoped review found no findings. Parser still validates protocol/host/repository identity, rejects duplicate identity fields and refuses fallback; advisory arrays do not change authority. No re-review needed. Delivery follows exact-head CI.
