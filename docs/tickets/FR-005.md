## Verification and limitations

Implemented 2026-10-27 on `fr-005-backup-restore`. Native SQLite online backup validates migration/schema, integrity and foreign keys before a trusted encrypted-storage hook sees the private snapshot. Migration 002 preserves migration 001 and existing v1 data, records pending/terminal attempts, and atomically links result events. Freshness conservatively ages the newest successful snapshot from attempt start, so late uploads cannot refresh old data.

Fixture evidence: a real AES-256-GCM synthetic hook encrypts the snapshot; the original database is closed/deleted; authenticated decryption restores a separate file through Core and compares actual run/inbox/event records. The snapshot correctly contains its own pending attempt. Corruption, invalid receipts, hook errors, failed final auditing, closed-state pending results, unsafe staging, plaintext cleanup failure, WAL transaction consistency, v1 upgrade and stale/clock-skew states are covered. Targeted backup suite: 23 passed. Final `npm run check` passed: 194 tests, build, lint and format verification. `npm run typecheck`, local Markdown link validation, and `git diff --check` passed; migration 001 is byte-for-byte unchanged from main. Clean-install coverage checks schema v2 and Core backup/integrity exports.

The restore procedure and live prerequisites are documented in [backups](../backups.md). No actual off-host destination, real credentials, schedule, retention enforcement, production hook or production restore was provisioned. A hook acknowledgement is trusted evidence, not independent remote verification. Independent review found no critical/important findings; its minor v1 fixture coverage request was addressed by preserving/asserting a completed run and linked historical event, including null backupId. PR/CI/merged-main verification follows before Done.
