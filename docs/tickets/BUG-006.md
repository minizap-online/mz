# BUG-006 — Make provisioned projects ready for steward conversations

Repository provisioning omits ARCHITECTURE.md, DECISIONS.md and tasks/steward.md,
which the context compiler requires for project-scoped ask. A successfully
provisioned project therefore fails conversation preparation.

## Acceptance

- Create and attach seed the complete project context without inventing a brief.
- Replaying a successful provisioning action fills missing files without another
  provider mutation and preserves existing owner knowledge.
- Existing task directory aliases are rejected before writing through them.
- A regression exercises project-scoped conversation preparation after provisioning.

## Evidence

Registered before implementation. Source tracing confirms the producer/consumer
mismatch; a metadata-only check of the reported project confirmed the three
required files are absent. Live settings validation also fails in this restricted
session, so end-to-end live verification remains separate. No private content or
credentials are included here. GitHub synchronization pending access.

Implemented complete context scaffolding in the shared create/attach publication
path. Existing files are preserved; a successful journal replay repairs missing
files without provider calls. Task directory validation rejects symlinks before
any writes through that directory.

RED: the new project conversation test failed with the reported preparation
message, and the directory-alias test failed because provisioning accepted the
alias. GREEN: all six provisioning tests pass, including actual printable owner
conversation preparation and repair replay. `TMPDIR=/var/tmp npm run check`
passed build, lint, formatting and 482/482 tests; `npm run typecheck` and
`git diff --check` passed. Tests used /var/tmp because an unrelated /tmp/.git
marker correctly triggers private-storage rejection.

Outside the restricted session, actual saved settings validated successfully.
Repaired the reported project's missing context by replaying its recorded
successful action through Core with remote provider methods disabled. Its real
`ask --project ... --print` preparation now succeeds; no model was started or
remote repository changed. The installed development launcher uses this checkout's
rebuilt output, so retrying the original command uses the fix. Interactive Codex
execution was not tested. Independent review and GitHub synchronization remain
pending; no commit or PR was created in this session.

Follow-up: the second reported project had the same three missing context files.
Replayed its successful provisioning record through Core with remote operations
disabled, preserving existing notes. Its actual project-scoped printable owner
conversation now prepares successfully too. No interactive model session was
started. The source fix is unchanged; no additional test run was needed for this
existing-project repair.
