# FR-016 — Guide project repair and onboarding through the steward conversation

## Outcome

The owner uses `mz ask` to recover incomplete project context, introduce existing
projects and discuss integration with company conventions. The steward inspects
available evidence, asks about meaningful unknowns, and can apply concrete workflow
changes after the owner agrees to the proposal. Existing projects remain usable.

## Scope and dependencies

Builds on FR-014 conversations, FR-015 repository provisioning and BUG-006 complete
project scaffolding. This is bounded M-05 owner-assisted onboarding, including
explicitly authorized work in a separate project checkout. It does not implement
M-06 worker launching, scheduling or unattended issue processing.

[Design](../superpowers/specs/2026-10-30-steward-project-onboarding-design.md).
The owner selected conversational entry through ask and authorized preparing the
design and implementation scope. The owner approved the written design on
2026-10-30. [Implementation plan](../superpowers/plans/2026-10-30-steward-project-onboarding.md).

## Acceptance

- [ ] An incomplete or unknown selected project can start a bounded onboarding
      conversation without weakening strict context compilation or inventing facts.
- [ ] Missing files are distinguishable from malformed, unsafe or inaccessible
      files. Recovery preserves existing knowledge and project behavior.
- [ ] The steward can inspect an explicitly selected existing repository, describe
      its purpose/workflow with evidence, and resolve important unknowns with the owner.
- [ ] Accepted context and outstanding questions persist privately across sessions.
- [ ] Workflow changes use a concrete proposal, explicit repository issue and
      approved scope; stale proposals are reconciled before writes.
- [ ] Approved patches stay in the separate project checkout, preserve unrelated
      edits and use bounded host authority and repository-scoped credentials.
- [ ] Read-only and print modes preserve their existing restrictions; repository
      content cannot grant authority, execute setup scripts or leak private context.
- [ ] Deterministic tests cover preparation, repair, preservation, unavailable
      prerequisites, scope and patch safeguards; behavioral evaluations cover actual
      steward reasoning and truthful handoffs separately from launch wiring.
