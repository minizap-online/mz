# FR-018 — Allow related projects to read code and coordinate through issues

## Agreed scope and implementation plan

The owner selected sibling code read and ticket coordination for a game and its
asset generator. Each session retains delivery authority over its own repository.
An explicit same-organization related-repository allowlist permits Contents read,
Issues write and Pull requests read on siblings. No sibling code/workflow/settings
write or cross-repository PR creation is granted. Unlisted repositories stay denied.
GitHub tokens remain restricted to the single repository used by each operation.
The existing trusted same-user host limitations remain explicit.

The requesting project opens an asset-generator issue describing its requirements;
the generator returns versioned artifacts/output and links its result to that
ticket. The requesting project handles integration and its own PR. Automatic
generation or a generator-authored PR into the consumer is not implemented here.

Advanced checkout syntax: `mz project checkout NAME DIRECTORY --delivery --related
SIBLING`, repeatable for up to eight explicitly named sibling repositories. Owners
may ask the steward conversationally; this is not an automatic organization grant.
Related repositories are recorded as nonsecret local activation/handoff context.

1. Add a separate provider collaboration token profile and CLI target routing, with
   RED/GREEN tests proving one-repository read-code/write-issues tokens and denial
   of unrelated targets.
2. Add explicit checkout relationship options, migration of recognized managed
   helper/activation files and session Git overrides. A primary session must not
   pick up a sibling checkout's full-delivery helper through `git -C SIBLING`.
   Preserve custom files, retain missing-only handoffs and document the boundary.
3. Verify full checks/review, install, configure the actual pair and verify native
   Git and issue access. Record the relationship privately, without publishing
   company configuration in this repository. No product code or deployment changes.

## Acceptance

- [x] Primary delivery and sibling collaboration profiles are distinct.
- [x] Git/gh route each approved target to a single-repository token; sibling
      credentials cannot write code, workflows or repository administration.
- [x] Explicit sibling/API targets work; unrelated/foreign/malformed targets fail.
- [x] Session Git overrides sibling local helpers, with safe managed-file upgrade
      and preservation of hand-edited files.
- [x] Handoffs describe ticket requests, results and integration ownership.
- [x] Synthetic checks, independent review and actual paired readiness recorded.

## Evidence

Registered before implementation after the owner chose read plus tickets. The
current single-project pin must be extended; a multi-repository token alone would
not fix it. No new GitHub App permissions are required for this subset. Native
workflow GITHUB_TOKEN cross-repository automation remains a separate capability.
Issue synchronization pending.

RED: collaboration profile and --related preparation failed before implementation.
GREEN: provider assertions verify exactly one repository ID, Contents/PR read and
Issues write, without sibling delivery grants. CLI regressions verify explicit
sibling issue/API routes and unrelated rejection, historical activation upgrade,
and primary-session override while Git runs in a sibling delivery checkout.
Independent review found no Critical/Important findings and one Minor: an edited
activation was validated after helper mutation. A RED preservation test reproduced
it; preflight now validates both managed artifacts before helper writes. All
focused tests pass. Final full check passes 495/495 tests plus build/lint/format;
typecheck and diff checks pass. No review finding deferred.

Installed the tested code and configured the owner-selected private pair. Both
activated sessions passed actual sibling Git HEAD, repository contents API and
issue reads with collaboration credentials. App grants were not expanded. Local
collaboration handoffs and private company architecture notes were updated without
overwriting product work. The owner then explicitly authorized notifying both
existing Codex sessions: metadata-only lookup identified one session per checkout,
and native `codex queue` confirmed both messages queued. Messages explain the
read/ticket boundary, linked asset requests/results, consumer-owned integration,
and re-sourcing activation in the same shell as each Git/gh command. No new agent
was started/resumed; no acknowledgment or completion by those agents is claimed.
