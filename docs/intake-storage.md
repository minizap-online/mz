# Private intake storage and retention

This is the M-02 implementation policy required by CR-002 before intake. It defines the default code boundary; organization-specific deployment/retention decisions remain in the private company repository.

Raw intake is untrusted private source material. Import a bounded UTF-8 Markdown copy into an explicitly selected private host directory outside Git repositories and outside disposable worker storage. The directory uses the existing trusted-host ownership/ancestor checks; operation directories are 0700 and files 0600. Do not put raw intake in the public implementation repository, private company Git history, SQLite, events, logs or CLI output. Do not deliberately ingest credential values; provision credentials through symbolic secret references. The filesystem source store is private data, not a secret manager.

Each successful import retains a UUID-named source directory containing exact `content.md` bytes and `metadata.json`. The manifest records structural item/source/actor identities, UTC receipt time, source kind/byte length, initial scope and optional original basename for a file source. The original source path is not retained. SQLite stores only the source UUID, item metadata, actor, bounded scope, source kind/byte count and fixed pending-summary status. The source directory is looked up from explicit host configuration, not a stored user path.

Default retention is **retain until explicit operator removal**, including after triage. There is no automated purge, TTL, compaction, hidden background process or permission to delete the original document. The operator may apply an approved shorter retention policy through private host procedures, coordinate with readers/backups, and preserve append-only event history after source removal. Per-import content is capped at 1 MiB; host quotas, monitoring, encrypted source-store backup and retention operations remain operator responsibilities. No deployment or retention schedule is provisioned by the feature.

Source files are durably written before the SQLite transaction that creates inbox/metadata/event. A failed transaction cleans only the directory owned by that attempt. A crash may leave an orphan directory; its manifest contains the intended item UUID for deliberate reconciliation through Core. A committed inbox must not refer to a partially written source under normal successful operation. This ordering is not a distributed filesystem/SQLite transaction. Do not automatically delete unknown or in-flight directories. Filesystem corruption, deliberate administrator mutation, cross-database misconfiguration or storage loss still require operational recovery. SQLite backup alone does not back up the raw source store; recover both with matching source identities.

Ingest accepts data, not authority. It does not parse Markdown instructions/front matter as commands, invoke an LLM, call a provider, change project activation or grant capabilities. The summary is a fixed pending placeholder, never an input-derived value in SQLite or diagnostic output. Scope is classification metadata only; `project:<id>` neither proves a project exists nor authorizes work.

Publication is a separate deliberate promotion: review and sanitize a proposed work item, choose its destination/visibility, enforce the actor's capabilities, create it through a real audited provider, and record the provider reference. Ingest and local triage perform none of those remote actions. Raw sources remain private even when a sanitized derivative is deliberately promoted. Project activation and organizational authority changes retain the human boundary. No automatic promotion is implemented in M-02.
