# FR-003 Runtime state adapter

## Scope and approach

Deliver MZ-003: SQLite migrations, event/inbox/run storage, WAL, transactions, and a worker-facing Core boundary. The owner authorized this ticket on 2026-10-27. API/schema choices below are implementation decisions within that scope. No actual organization database is provisioned, no CLI command or provider integration is added, and no backup/restore or secret provider is implemented.

Use Node 24's built-in SQLite driver, avoiding a native npm dependency. `@mz/state` contains an integration adapter, internal migration engine, and driver-independent types. `@mz/core` constructs it and exposes only typed operations. There is no raw connection or SQL method on the returned API. This is an embedded control-plane API, not a new service or a replacement for later capability enforcement.

## First schema and data boundary

The first schema stores structural metadata only:

- `events`: increasing integer sequence, unique UUID id, enumerated event type, actor UUID, UTC occurrence timestamp, optional run/inbox UUID references.
- `inbox_items`: unique UUID id, source UUID reference, receipt timestamp. Source content is kept elsewhere; no work priority/status/title/body fields.
- `runs`: unique UUID id, worker UUID, start timestamp, nullable finish timestamp and enumerated outcome (succeeded, failed, cancelled).
- `schema_migrations`: contiguous version, name, SQL SHA-256 checksum, application timestamp.

Record and actor/source/worker references are canonical lowercase UUIDs. Timestamps use canonical ISO UTC with milliseconds. IDs and timestamps may be caller-supplied for deterministic replay, or record IDs/timestamps are generated by Core. IDs are references, never credential values. Reject unknown fields, arbitrary objects, free text/payloads, noncanonical identifiers, and invalid timestamps before persistence. FR-004 will add secret reference/resolution/redaction contracts; this ticket does not claim a universal detector for credentials mislabeled as identifiers. No token, raw intake, transcript, resolved-secret, or arbitrary serialized payload field exists.

Supported event types are the initial design's event vocabulary plus `run.started` and `run.finished`. Stored run outcomes describe execution, never GitHub work-item status. `startRun`, `finishRun`, and `createInboxItem` append their audit event atomically. `appendEvent` supports other structural audit observations.

## Core contract

`openRuntimeState({ path }): RuntimeState` opens an explicit absolute file path; its parent must already exist. No default path or in-memory store is accepted. New files use mode 0600; existing database symlinks/nonregular files fail. No company-specific location is hard-coded.

Operations are synchronous and return detached records:

- `appendEvent({ id?, type, actorId, occurredAt?, runId?, inboxItemId? })` → event.
- `createInboxItem({ id?, sourceId, actorId, receivedAt? })` → inbox record plus internal inbox.created event.
- `startRun({ id?, workerId, actorId, startedAt? })` → run plus run.started event.
- `finishRun({ id, actorId, outcome, finishedAt? })` → terminal run plus run.finished event. A run finishes once, no earlier than its start.
- `getRun(id)`, `getInboxItem(id)` → record or null.
- `listEvents({ afterSequence?, limit? }?)` → sequence-ordered cursor page; defaults 0/100, limit 1–1000.
- `transaction(work)` → result of a synchronous callback receiving the same record/query operations (without transaction/close/status).
- `getStatus()` → schema version, WAL mode, foreign-key enforcement.
- `close()` is idempotent; subsequent operations fail.

Callbacks cannot be async/thenable, nested, or use the outer API during a transaction. A scoped transaction cannot escape its callback. Any failed operation poisons the batch even if caught in the callback. Callback failures roll back and surface a safe error without retaining user error messages. No partial record/event pair is committed. No API mutates/deletes existing events or inbox records. Returned records can be changed by callers without changing stored data.

## SQLite and migrations

Bundle SQL migrations with the state package so a clean installation works from any cwd. Document their schema under schemas/. Each future schema change adds a migration; do not edit an applied migration. Validate database application identity, user version, contiguous migration names/checksums, and required schema objects; reject foreign, future, or inconsistent databases without treating them as empty.

Enable and verify WAL, foreign keys, recursive triggers, FULL synchronous durability, and a bounded busy timeout. Check identity before changing an existing foreign database's journal settings. Apply pending migrations under BEGIN IMMEDIATE with the ledger/version change in the same transaction. Reopening is idempotent. Migrations with a later failing statement roll back all DDL and ledger/version updates. Internal migration tests may use a real synthetic SQLite connection and custom migration lists; workers never receive that connection.

SQL triggers reject UPDATE/DELETE on events and prevent INSERT OR REPLACE collisions even when another connection disables recursive triggers. Foreign keys link event run/inbox references. Transactions use the same single-writer connection. WAL visibility and lock contention are tested with a second connection. This does not harden the database against an administrator dropping triggers.

`RuntimeStateError` exposes stable codes and optional known field names, never raw SQL/driver messages, user values, callback errors, or causes containing them.
