# Organization-owned GitHub App

MZ can connect once to an organization-owned App, then use short-lived credentials for company Git and project repository provisioning. Your human organization Owner role stays independent: the profile requests Members read only, excludes organization/repository Administration, and never signs in as your personal account. It cannot remove or demote members through its GitHub grants. See [the approved design](superpowers/specs/2026-10-28-github-app-owner-access-design.md).

## First connection

Run `mz init --repository https://github.com/OWNER/company.git`, choose **app**, and follow the private setup-page link. For a local company shell without an existing remote, use `mz init --github-auth app`. GitHub SSH clone URLs such as `git@github.com:OWNER/company.git` are accepted too: App mode announces the HTTPS transport, verifies any existing fetch/push URLs identify the same repository, and binds them to HTTPS for App authentication. Git URL rewrite rules that would turn the effective App transport back into SSH are rejected before credential setup; adjust the scoped Git configuration before retrying. Explicit existing/OAuth SSH modes retain their own transport. MZ prepares the actual manifest, including permissions, rather than asking you to configure scopes from memory. In GitHub, register the private App on the organization and install it for **All repositories**. Keep MZ running until GitHub returns you to the setup page; then return to the terminal and continue with `mz guide`.

The wizard asks only the technical organization name and the human GitHub username to protect. Company purpose, project brief, devbox context and team questions belong in guide/ask. No personal user OAuth authorization is requested by the App flow. Webhooks are explicitly inactive and no events are subscribed. The manifest supplies the public MZ homepage as an unused webhook placeholder for GitHub validation; the private browser callback and installation return still use your local tunnel. No public webhook receiver is needed. You remain able to suspend/uninstall the App directly in GitHub.

The setup server binds only devbox loopback, uses an unguessable single-use state, checks Host/Origin, avoids access logs and closes after ten minutes. If your browser runs on another machine, forward its displayed loopback port through your devbox's Ports UI. A fixed forwarded port can be selected with `--github-setup-port PORT`; `--github-setup-origin URL` supports the browser-visible HTTPS origin or forwarded HTTP localhost origin. MZ prints the SSH forwarding command for the active ports and says to run it on the browser computer in a separate terminal. Set optional `MZ_SSH_DESTINATION` to your normal user@host or SSH alias to fill the destination; otherwise replace the clearly labelled placeholder and reuse any normal -J/-p options. The `-N` command stays open without a shell prompt; keep it and init running, then open the printed localhost link rather than the devbox network IP. No automatic tunnel or public listener is created. This is one-time connection work; normal projects do not require new personal tokens or another installation. A local-only loopback link is not usable from a remote browser until forwarded.

For an existing registration, `--github-app-file /absolute/protected/app.json` imports an owner-only file outside Git/company knowledge. Its schema1 JSON contains numeric `appId`, `installationId`, `organizationId`, `ownerId`, strings `organization`, `owner`, and PEM text `privateKey`. Enter these only in the protected file, never company conversation. MZ verifies the key, installed App permissions and active owner identity before publishing the connection. The registration's private visibility must be reviewed in GitHub: the manifest sets it, but GitHub's App REST response does not expose that setting. Import sources are retained under your secret-retention policy.

An interrupted registered App can be resumed: finish its installation using the link already shown by GitHub and rerun init. MZ reuses the protected pending key and verifies the installation before making the connection active. Before showing registration, MZ persists a protected `registration.json` intent. If a return/conversion response is lost before key receipt, rerunning init requires recovery/import of that existing registration instead of exposing a new registration. If GitHub rejected the registration form before creating an App, init asks for explicit confirmation and reuses the saved technical organization/owner selection while replacing only the registration intent. Default/no confirmation preserves the intent for recovery/import; pending keys and working connections are never cleared by this path. Never discard an uncertain registration merely to retry. MZ does not silently create another App or revoke one.

## Permissions and credential boundary

The profile grants repository Metadata read; Contents, Issues, Pull requests and Repository creation write; organization Projects write; and Members read. Unknown or broader grants are rejected. Repository creation uses its dedicated permission rather than Administration. No member/team/collaborator mutation, repository deletion/transfer, billing, broad administration or user account API is exposed. Repository rule administration remains a direct human configuration step. Workflow edits, deployment secrets and other delivery capabilities are not silently included; they need a separately reviewed connection profile when the concrete delivery workflow requires them.

The App key and schema1 connection metadata live in the private `github-app/` directory alongside the selected MZ config, outside Git/company knowledge. The key is an owner-only unencrypted host file. Only a profile/helper reference is saved in local company Git metadata, explicitly marked `mz.github.version=2`; existing PAT bindings remain version1 and are not treated as App credentials. Existing local settings and SQLite schemas are unchanged. There is no automatic App-to-PAT downgrade or credential fallback after a failure. Git helper failures return the terminal `quit=true` response; App client environments disable askpass and terminal credential prompts.

MZ checks the App and installation grants, organization IDs and protected owner role before issuing credentials. Git operations use an explicit repository ID and the Contents/Issues/Pull requests subset; organization-level creation and membership checks use separate narrow control-plane credentials. Tokens expire within an hour and are not saved in the connection file. The native Git helper speaks Git's credential protocol; it is not a model-facing token API. The private gh launcher supplies a repository-scoped token only to the native child. It supports repository-oriented api/issue/pr/repo/run/workflow/release commands within installed grants; `gh auth token`, user-auth operations, absolute API URLs and hostname overrides are rejected. Native children also have shared Secret Service keyring access disabled; the parent Codex session retains its normal D-Bus access. Use `mz github status` for App identity, because App installation credentials do not identify a personal user through `gh api user`.

The current steward is a trusted host operator. Owner-only files and prompts do not isolate untrusted code running as that same OS user. Before using untrusted workers, put the signing key/broker behind a separate host principal or equivalent enforced boundary. That worker isolation/scheduling is not implemented by this pilot feature. Do not put owner/admin tokens in workflows or runners reachable through App-writable code.

## Project workflow

FR-017 adds [prepared checkouts and an explicit repository delivery profile](project-checkout.md).
The original profile described above remains valid. Only an explicit delivery
upgrade adds repository Administration, Actions, Workflows, Environments,
Deployments, Pages, Secrets, Variables, Checks and Commit statuses write. Worker
tokens remain restricted to one repository and exclude organization grants.
Run `mz github permissions` before changing the existing App's grants; GitHub
installation approval remains required. Default init still requests the original
profile and does not silently expand authority.

Tell the steward what to build through `mz guide` / `mz ask`. It can use `mz project --help` to prepare an owner-authorized create/attach operation. The advanced API is `mz project create NAME --approved`, default private; `--public` additionally selects explicitly approved public visibility. `--approved` is the trusted host operator's assertion about the owner's request, not a security gate for an untrusted worker. Project names use lowercase slugs.

MZ creates the repository, records durable structural action evidence through Core, and adds repository references and initial project notes under company `projects/NAME/` while preserving existing owner knowledge. Repository provisioning does not prove development, deployment or the complete website brief. The owner/steward still records purpose, scope and actual project activation/context; no DNS, spending or deployment occurs just from repository creation.

Provisioning seeds the project configuration, brief, architecture, status, decisions
and steward task needed by `mz ask --project NAME`. After updating MZ, rerun the
same successful create/attach command (with the original `--action` if supplied)
to fill missing context files in older projects. A recorded successful action is
replayed locally without another repository creation; existing owner notes are
preserved. This recovery does not apply to uncertain remote outcomes, which still
require the explicit reconciliation described below.

Retries use a stable action identity, optionally supplied with `--action UUID`. Core's version1 private provisioning journal is under the configured source-storage directory, outside Git; intent, attempted mutation and successful outcome are immutable files. The new format has no predecessor to migrate, and rejects unsupported versions; it does not add an editable task tracker or store secret/content payloads in SQLite. Permission/audit failures do not cause remote writes. If the remote may have created a repository before a timeout or local result persistence failure, MZ blocks another create attempt under that action. Inspect the repository and explicitly authorize `mz project attach NAME --approved` to reconcile. It never adopts an unrelated same-name repository or automatically deletes resources as rollback.

No real App registration, installation, permission change or project activation is performed by development verification. Synthetic tests and actual owner setup are separate evidence.

If browser setup completes but init fails at repository connection, the saved App connection is retained. Rerun init with the same company directory/repository and App method; no new registration, rejected-form confirmation, tunnel or personal token is needed for that resume. Git credential capability/challenge/state arrays are advisory; the helper ignores them while validating protocol, host and repository identity strictly.
